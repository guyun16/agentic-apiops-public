- Prefer the most specific validated RAG_EVIDENCE itemId over an aggregate

- Keep the Java TestReport failureType as an immutable observed execution fact. The
  DiagnosisReport `failureType` is a separate Agent-authored semantic diagnosis and
  need not copy the observed value. For example, a Runner-successful HTTP 409 with
  explicit business-error evidence may be diagnosed as BUSINESS_ERROR, while an HTTP
  500 response may be diagnosed as SYSTEM_ERROR. This never changes the Java fact.
- Do not mechanically copy Java `NONE` into DiagnosisReport when the authoritative
  step facts contain an error HTTP response. Conversely, never infer a semantic class
  merely from task wording; require the report response or cited bounded evidence.
- Keep symptom, observed fact, root-cause hypothesis, and recommendation distinct.
- Rank authority as: observed execution facts, then validated retrieval evidence, then
  model inference. Never override an observed fact with an inference.
- An HTTP response status is an HTTP observation; a timeout, DNS, connect, TLS, or I/O
  failure without a response is a transport observation. Do not conflate the two.
- Apply this semantic decision order to authoritative facts: an observed HTTP 5xx
  response is SYSTEM_ERROR, not NONE or CONNECT_ERROR; an observed documented HTTP
  4xx business response is BUSINESS_ERROR unless specific bounded evidence proves a
  narrower ontology such as DATABASE_CONSTRAINT_ERROR; a no-response DNS/connect
  mechanism is CONNECT_ERROR unless the output contract explicitly supports a more
  specific transport class. ASSERTION_MISMATCH describes the assertion layer and is
  not a root-cause ontology when a more specific response fact is available.
- An assertion mismatch proves only that actual differed from expected. Claim a
  business, server, database, or upstream cause only when bounded evidence supports it.
- Insufficient-evidence contract: insufficient-evidence-v1.
- Separate three levels: observed failure facts, evidence-supported provisional
  mechanisms, and confirmed specific root causes. Keep known failure facts in summary
  even when no defensible mechanism hypothesis can be formed.
- sufficientEvidence=false does not require an empty rootCauseHypotheses array.
  Empty hypotheses are allowed when no defensible hypothesis can be formed; explain
  that boundary in limitations and state the discriminating next check.
- Nonempty hypotheses require evidence supporting each proposed mechanism. Explicitly
  describe them as provisional in statement; never state an unverified cause as fact.
  LOW/MEDIUM confidence, an existing citation ID, and nonempty limitations do not prove
  that a statement is supported. Cite the evidence that supports the claim itself.
- When evidence is missing or conflicting, preserve the observations, do not resolve
  conflicts by guessing, and set sufficientEvidence=false unless independent evidence
  establishes the specific cause. A conflict label is not two conflicting observations.
- With sufficientEvidence=false, every hypothesis confidence must be LOW or MEDIUM,

- With sufficientEvidence=true, state the specific root cause and cite independent
